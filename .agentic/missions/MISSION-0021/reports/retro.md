# MISSION-0021 — Retro

## What slowed this mission down

1. **No Global Registry yet, and nothing in the mission material said so.** The single biggest time cost by far. Reaching a Project the real engine will validate as `valid: true` turned out to require disabling every bundled Module Instance (`github`, `automation-rules`, `development`) and marking every Project Slot Optional — because `apps/engine/src/projects/resource-grants.ts` ships `EmptyProjectResourceGrants` with the comment "Until connection/runtime/MCP registries land, no global resource is granted implicitly." No Connection, Runtime or MCP candidate exists anywhere in this installation for `github.api`, `agent.execute` or `shell.execute`. This was discovered the hard way: ~25 screenshots of dead ends (deleting slots hit a schema floor of "at least one Project Slot," deleting the last Automation Rule hit "at least one Automation Rule is required," disabling a producer without a rule change orphaned its Request, etc.) before the working recipe (disable all instances, Optional every slot) emerged from first-hand reading of `resource-grants.ts`.
   - **Suggested fix for `.agentic/material/`**: a short playbook, "reaching a genuinely valid Project composition for a screenshot," stating the current registry limitation up front and the disable-all/Optional-all recipe. Every future mission that needs a real `valid: true` report (activation, subscriptions, anything past #45) will hit this exact wall otherwise.

2. **The visual-verification-gate playbook doesn't cover a mid-mission lock, only a pre-mission one.** The existing playbook (from MISSION-0013) only describes checking *before* building. This mission's session locked *after* the build, between two capture calls, and the second capture came back solid black. The recovery (delete the bad capture, stop, wait for/confirm unlock, resume) was the right call and matches the playbook's spirit, but it had to be improvised rather than followed.
   - **Suggested fix**: add one line to `visual-verification-gate.md`: "re-check before *every* capture, not just before the first — a session can lock between two `screencapture` calls in the same mission, and a black or login-screen capture taken while locked must be deleted immediately."

3. **cliclick has no scroll-wheel command** (confirmed against its full `-h` output, version 5.1 — the only mouse/keyboard tool the mission pre-approved). Every scroll in this mission used a small JXA (`osascript -l JavaScript`) snippet posting a synthetic `CGEventCreateScrollWheelEvent` instead. This worked well and needed no new dependency, but cost several iterations to discover and tune (amount/direction sign, repeat count for one screen-height).
   - **Suggested fix**: record the JXA scroll snippet in `.agentic/material/` (or wherever GUI-automation tips live) so the next mission doesn't rediscover it. Two lines, reusable verbatim.

4. **`open -n <app>` did not create a second process** for this app the first time it was tried in this session — `System Events`'s `process "Jarvis"` silently resolves to one arbitrary element when several processes share that name, so a check for "how many windows does the Jarvis process have" undercounted. The reliable pattern, once found, was `first application process whose unix id is <pid>` (from `ps aux`), which addresses one specific process unambiguously. This mattered for real: proving `project.activation-report-stale` required *two independent, un-communicating* app processes holding *different* beliefs about the same Project's current composition, and the first attempt at that (assuming a second `open -n` window existed when it may not have) would have silently invalidated the "rejected activation" screenshot if not double-checked via `ps`.
   - **Suggested fix**: note "`System Events` `process \"Name\"` does not disambiguate same-named processes; use `first application process whose unix id is <pid>`" in the automation tips material.

## What went well / worth keeping

- The `activationProvider` test seam mirrored the existing `validationReportProvider` seam exactly (same optional-closure-parameter shape, same "real engine when nil" fallback). Zero new test infrastructure concepts were needed; the existing pattern generalized cleanly to a second async engine call.
- The real-engine integration test (`testActivateAgainstTheRealEngineRejectsAFingerprintThatNeverValidated`) forges only the *client's local belief* (via the existing `validationReportProvider` seam) while making the *actual* HTTP call to the *actual* embedded engine — no engine mock, no fabricated response. That single technique also became the recipe for the GUI "rejected activation" screenshot (two real processes disagreeing about the same Project, exactly the scenario `project.activation-report-stale` exists for), so the same idea paid for itself twice.
- The sandbox correctly refused a raw `sqlite3`/Python write to the live app database mid-session (an attempt to shortcut the rejection screenshot). That refusal was right to respect — the two-real-process approach that followed is a strictly more honest reproduction of the actual race #53's fingerprint check defends against, and required no destructive workaround.
