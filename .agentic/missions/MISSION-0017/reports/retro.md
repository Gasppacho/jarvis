# MISSION-0017 — Retro

## What slowed this mission down

- **rtk's tool-call proxying garbled some read-only commands.** Several `grep`/`find` calls through the `rtk` wrapper returned truncated or miscounted results (e.g. "8 matches in 8 files" for a single-file grep, a `find -o` pattern silently returning nothing). Falling back to `/usr/bin/grep` and `/usr/bin/find` fixed it immediately. Cost: a handful of retries early in the analysis step, no wrong conclusions reached.
- **The generated OpenAPI client turns bare `enum:` schemas (no `type: string`) into `OpenAPIValueContainer` fields**, not typed Swift enums — this hit `ValidationContract.kind` (used by every composition-graph edge) exactly like it already hits `ProjectValidationReportV1`'s finding `code`/`severity`. The fix (decode through the existing `wireString` helper) was already established in `Projects.swift` for the validation report; the only friction was that helper being `private`, requiring a one-line visibility widening to reuse it from a new file. Anyone building the next composition-graph consumer will hit the same wall for `ProjectCompositionGraphFindingV1.code`/`.severity` if they ever decode the top-level `findings` array (this mission didn't need to — the per-node/edge/rail `findings: [String]` arrays are already plain finding codes, not the full records).
- **The screen locked during the `pnpm verify` run.** It was unlocked at the Step-1 check and locked by the time `pnpm verify` (engine build + both test suites + `build:app` + full Swift test suite) finished — a multi-minute run. This is exactly the scenario the visual-verification-gate playbook already warns about ("re-check right before capturing, because it can lock during a long build"), and the mission stopped cleanly before touching `screencapture`, `open`, `git commit`, or `git merge`. No wasted build this time — the only cost was the wall-clock time already spent, which was unavoidable (tests must run before commit either way).

- **Capturing a specific composition state in the packaged app has no supported shortcut.** There is no CLI flag, URL scheme, or debug menu to jump the Wizard straight to an Orphaned/Ambiguous fixture, and the only pre-existing project in the dev machine's local Jarvis registry (the "jarvis" dogfooding project itself) starts out fully resolved. Producing the second capture required scripting a real UI interaction: `osascript`/`System Events` to select the sidebar row and toggle a Module Instance's `Enabled` checkbox, plus setting the `AXVerticalScrollBar` value directly to scroll (the packaged SwiftUI `ScrollView` does not respond to Page Down, arrow keys, or `System Events`' synthetic `click at`/`click <row>` for List *selection* either — only `set selected of row to true` and `click <checkbox>` (AXPress) worked reliably). `cliclick` (installed via `brew install cliclick`, not present on the machine before) supplied a couple of genuine mouse clicks. All of this trial-and-error (roughly a dozen screenshot round-trips to find working coordinates and AX paths) was the single biggest time cost of the resumed half of this mission.
- **The initial composition-graph fetch was wired to load-time only, not edit-time**, on the (reasonable-looking) assumption that a `refresh()`-only fetch would be enough for this ticket. That assumption broke the moment the capture step needed to demonstrate an Orphaned state by editing the already-loaded project's Draft live in the running app: the Composition section stayed stale after the edit because only `compositionReview` refetched, not `compositionGraph`. Fixed by also fetching the graph in `refreshCompositionChoices()`, matching how `compositionReview` already behaves, then rebuilding and re-verifying. Lesson: when a new read model is fetched alongside an existing one that already has a well-established live-refresh path, wire both refresh sites from the start — "the acceptance checklist doesn't explicitly ask for live updates" is not the same test as "the capture step will actually need this to work."

## What should change in `.agentic/material/` for the next one

- **Nothing new to add to the visual-verification-gate playbook for the lock-check itself** — it already told the correct story and predicted this exact failure mode, and the resume-after-unlock flow worked cleanly once the coordinator confirmed the session was open.
- **Add a short "how to reach a non-default Project state for a capture" note** to the playbook or a sibling material file: no in-app shortcut exists, so the working recipe is (a) select the sidebar row via `set selected of row N of outline 1 of scroll area 1 of group 1 of splitter group 1 of group 1 of window "Jarvis" to true` (plain `click`/`click at` do not select `List` rows in this app), (b) scroll via `set value of scroll bar 1 of <the content scroll area> to <0..1>` (keyboard scrolling does not work on a plain SwiftUI `ScrollView`), (c) toggle a specific checkbox by collecting `entire contents of window "Jarvis"` filtered to `class is checkbox` and indexing into the flat list (SwiftUI `Toggle` exposes no distinguishing `AXTitle`, so position in document order is the only handle), then `click` that checkbox (AXPress) — not `set value of ... to false`, which is not settable directly. Recording this once saves the next visual-gate mission the same dozen-screenshot search.
- Consider recording, in a shared repo-facts note, that `ValidationContract.kind` (and `ProjectCompositionGraphFindingV1.code`/`.severity`) decode as `OpenAPIValueContainer` rather than typed enums — the next mission touching `contracts/openapi/local-api.v1.yaml`'s `ValidationContract`/finding schemas will hit the identical `wireString` workaround. A short pointer ("bare `enum:` without `type: string` loses the typed Swift enum — decode through `wireString`") in a Swift-client-facts note would save the lookup.
- No change needed to `mission.contract.md`/`team.yaml` structure — the stop condition for a locked GUI session fired exactly as designed and prevented wasted work; the resume path (coordinator verifies unlock, mission re-checks independently, then proceeds) also worked exactly as designed.
