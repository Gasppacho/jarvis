# Remise à plat du parcours projet — 16 septembre 2026

> Plan historique remplacé par l'ADR 0020 et le parcours courant
> **Workflow → Paramétrage → Vérification**.

## Cible

Un débutant choisit un dépôt, voit le workflow qui sera réellement créé, confirme ses commandes et ses accès, comprend les corrections nécessaires, puis active explicitement une portée vérifiée. À tout moment, l'écran répond à trois questions : **où j'en suis**, **ce qui manque**, **quelle action faire maintenant**. La composition libre et les détails des contrats restent accessibles dans les réglages avancés.

Le guide canonique reste **Dépôt → Workflow → Accès et agent → Vérification**. Un brouillon incomplet est enregistrable ; aucune étape de configuration ne lance un agent, ne pousse de branche ou ne crée de PR. La relecture et le merge restent humains.

## Preuve de cette passe

Application empaquetée lancée dans une instance isolée avec `--data-root`, dépôt Git temporaire muni d'un remote GitHub fictif et fenêtre native en apparence sombre. Parcours exécuté : premier accueil → sélecteur macOS → inspection → création du brouillon → ajout de GitHub → ajout de Développement → cartes Développement et Vérifications → Accès et agent → préflight → action Corriger → Dépôt. Les captures de cette passe sont conservées dans `.scratch/ux-final-pass-20260916/`. Aucun compte ni runtime n'a été lié au projet fictif ; aucune activation ni exécution externe n'a eu lieu. L'instance réelle et ses données ont été laissées intactes.

| Étape | Constat observé | Conséquence |
| --- | --- | --- |
| Import | Le sélecteur et la fiche d'inspection natifs sont compréhensibles ; le remote est coupé dans la fiche étroite | Difficile de vérifier deux dépôts aux noms proches |
| Workflow, GitHub seul | Badge « Prêt à revoir », titre « Développer une issue GitHub » et quatre cartes jusqu'à la PR | Le dessin promet un workflow que le brouillon ne contient pas |

| Accès et agent | Les comptes et Codex sont lisibles, mais leurs choix apparaissent aussi dans le Workflow | Deux lieux d'édition pour la même autorisation |

La passe n'établit pas la navigation VoiceOver complète, le comportement en petite fenêtre, ni le parcours avec de vrais accès GitHub/Codex. Les captures locales des tailles et apparences sont dans `.scratch/ux-alignment-20260916/` ; elles représentent une autre session.

## Plan, dans l'ordre

### 1. Enlever les blocages et les actions trompeuses

- Si le catalogue de modules charge mal, désactiver l'ajout et montrer l'erreur avec **Réessayer** dans le Workflow. Un clic ne doit jamais être sans effet.
- Garder une valeur de saisie transitoire pour la branche et la fréquence, puis valider au bon moment. Employer un `Picker` ou `Stepper` natif pour la fréquence bornée.
- Sur une migration qui exige la pause, proposer **Mettre le projet en pause** ou **Ouvrir la supervision pour le mettre en pause**, puis revenir au même guide ; expliquer les travaux encore actifs lorsqu'ils bloquent aussi.
- Harmoniser tous les libellés français, notamment l'aide GitHub qui dit « Réessayer » alors que le bouton dit « Actualiser les comptes ».

**Acceptation :** catalogue indisponible, valeur intermédiaire vide, dépôt historique actif et absence de compte donnent chacun une cause lisible et une action qui fonctionne.

### 2. Faire correspondre le dessin au brouillon réel

- Présenter dès l'entrée une action principale **Préparer le parcours recommandé GitHub → Développement → PR** qui ajoute les deux modules au brouillon, avec la possibilité explicite d'observer seulement les issues. Conserver ajout, retrait et désactivation des modules dans une zone de composition accessible.
- Montrer les quatre cartes comme **aperçu du parcours recommandé** tant qu'il n'est pas complet ; marquer chaque carte absente ou à configurer. Ne déclarer le Workflow « prêt à revoir » qu'après les choix de préparation et de validation requis pour le parcours choisi.
- Faire du Workflow le lieu des comportements (label, branche, préparation, validations) et d'**Accès et agent** le seul lieu de choix du compte et du runtime. Depuis le Workflow, un résumé « Accès à choisir » peut ouvrir directement cette étape.
- Une seule action principale par étape. Indiquer sur **Continuer** qu'il enregistre le brouillon, ou séparer clairement progression et enregistrement ; garder l'état Enregistré/À enregistrer visible.

**Acceptation :** GitHub seul n'annonce aucune PR future ; ajouter Développement change l'aperçu ; la réouverture retrouve les choix ; un utilisateur sait où régler chaque ressource sans rencontrer deux commandes concurrentes.

### 3. Rendre la vérification compréhensible et actionnable

- En haut, afficher une synthèse courte : **accès**, **préparation et commandes**, **déclenchement/portée**. Regrouper les contrôles Engine par étape de correction, retirer les doublons visuels et montrer d'abord l'impact en français. Garder l'intitulé et l'impact bruts du moteur dans **Détails techniques**.
- Un seul **Corriger** par problème utilisateur, qui ouvre l'étape et le contrôle concerné. Utiliser les identifiants structurés déjà fournis ; ne pas déduire la solution en analysant le texte anglais.
- Distinguer explicitement « configuration vérifiée », « commandes pas encore exécutées », « aucune issue prête » et « accès GitHub non vérifiable ». Le bouton final doit rappeler la portée exacte et rester indisponible sur rapport périmé.

**Acceptation :** avec compte, runtime, préparation et validations manquants, le premier écran tient dans une petite fenêtre et fournit des corrections distinctes ; les messages bruts restent consultables ; le rapport ne peut jamais autoriser une portée différente de celle affichée.

### 4. Polir l'interface macOS sans refaire le moteur

- Conserver `NavigationSplitView`, `NSOpenPanel`, les cartes illustrant le parcours, `GroupBox`, `DisclosureGroup` et les contrôles de progression natifs. Utiliser `Form` et `LabeledContent` pour aligner les réglages éditables, `Picker`/`Stepper` pour les valeurs bornées, et les rôles système pour les actions destructrices.
- Réduire les titres et textes répétés, placer l'action suivante près du contenu qu'elle conclut, rendre le remote complet copiable dans l'import, et laisser les détails techniques repliés. Vérifier la hiérarchie typographique, les marges et le défilement à 1100 × 800 et 1512 × 949, en clair et sombre.
- Tester l'ordre de tabulation, les noms VoiceOver, les états désactivés expliqués et la lecture de la correction complète. Les icônes restent accompagnées de texte.

**Acceptation :** les quatre étapes tiennent visuellement aux deux tailles sans contrôle caché derrière le pied de page ; toutes les actions sont accessibles au clavier et compréhensibles avec VoiceOver.

### 5. Réception sur l'app réelle

- Tests Swift ciblés sur les états du guide et la conservation du brouillon ; intégration Engine pour le preflight et la portée ; build de l'app ; parcours natif sur un dépôt temporaire : import, doublon, GitHub seul, parcours complet, erreurs de catalogue, accès absent, correction, retour et réouverture.
- Conserver des captures de chaque étape en clair/sombre et aux deux tailles, plus les observations clavier/VoiceOver. Vérifier séparément un projet historique à migrer.
- Le test GitHub/Codex de bout en bout exige un dépôt sandbox, un compte, une issue dédiée, un budget et un runtime autorisés. Le rapport distinguera ce test externe des contrôles locaux ; une activation ne sera pas simulée.

Chaque phase doit rester livrable et vérifiable seule. Mettre à jour `docs/product/UX.md` lorsque les décisions sont figées ; créer ensuite des tickets verticaux avec critères d'acceptation et dépendances. Ce document est un plan, pas une modification du comportement de l'application.
